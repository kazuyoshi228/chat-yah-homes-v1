# chat.yah.homes 開発経緯（2026-08-17 〜 2026-09-07）

宿泊ゲスト向けAIチャットサポートの立ち上げ記録。**なぜそう作ったか**を残すことが目的。
現在の仕様は各ドキュメント（`spec_*.md`）とコード、正本の所在は管理画面の SSoTマップを参照。

---

## 1. 出自と方針

**出自**: 稼働中の `chat.yah.mobi`（eSIMサポート・yah-chat-webdev）を複製し、宿泊事業向けに全面改修。
販売サイト連携（料金カタログ注入・注文/eSIM残量パーソナライズ・SSO）は全て除去した。

**Firebase構成**: yah.homes 本体と同一プロジェクト `yah-homes` に同居。
- Firestore named DB **`chat`**（chat専用・read/write）
- `(default)` DB は **read-only**（`property_facts` のみ参照）
- Functions は **codebase `chat`** で分離／Hosting は別サイト `chat-yah-homes`

**提供形態の決定（08/17）**: 埋め込みウィジェットではなく**単独ページ**。
`chat.yah.homes/{施設ID}` にQRコード・メール・OTAメッセージから直接アクセスする。
→ iframe/postMessage/親オリジン検証を全撤去でき、構成が大幅に単純化した。

**施設分離の決定**: プロジェクトは分けず `facilityId` でデータ分離。
初期は kiyokawa 1施設のみ公開しつつ、**DB・コードは最初から複数施設対応**で作った。
→ 結果、takasago 開通時にコード変更ゼロで済んだ（後述）。

## 2. SSoTファースト（このプロジェクトの背骨）

### 経緯

当初は施設情報を手書きRAG文書として投入していたが、レビューで**SSoT違反**と判明した
（規約や物件ページの内容をRAGにコピーすると、正本の更新でRAGが陳腐化する）。
yah.mobile で料金表をRAGに置いて誤案内事故を起こした経験と同型の構造だった。

### 到達した構成

| 情報 | 正本 | チャットへの経路 |
|---|---|---|
| 施設スペック・chat用情報（Q&A） | `admin/properties/{施設}/#chat`（property_facts.chatInfo） | 毎ターン read-only ライブ注入（5分キャッシュ） |
| 規約・ハウスルール | yah.homes/legal/terms | 毎日06:00 JST に自動同期 → RAG |
| 物件ページ・How-toページ・Local Guide | 各公開ページ | 同上 |
| チャット用写真 | 管理画面「写真」 | AIが質問に応じて添付 |
| 施設の公開フラグ・表示名 | chat_facilities（最小マスタ） | URL有効判定・ヘッダー表示 |
| 鍵・入室暗証番号 | property_secrets | 🚫 **チャットは読まない** |

**手書きRAGは段階的に全廃**（08/18）。現在RAGは自動同期6件のみで、二重管理はゼロ。
ルールとして「手書きRAGは他に正本が無い知識専用」を CLAUDE.md と管理画面に明記した。

### サイト自動同期（syncSiteSources）

- `chat_site_sources` にURLを1件登録するだけで対象追加（コード変更不要）
- sha256差分で変更時のみ更新 → 自動再Embedding
- 長いページは7,000字でチャンク分割（駐車場サイズが末尾で欠落した事故から実装）
- **JSレンダリングのページ対応**: how-toページは本文が `<script>` 内の多言語辞書にあり、
  静的抽出では689字しか取れなかった。script内の文字列リテラルから人間向けテキストを
  収穫するフォールバックを実装（5,169字を取得）

## 3. 安全設計

- **鍵・キーボックス暗証番号は構造的に遮断**: chat は `property_secrets` を読まない。
  プロンプトでも明示禁止し、SIMで毎回検証（機微情報の非開示 5/5）
- **Wi-Fiは方針転換で「案内する」に**（08/17）。鍵情報とは分離したルールに整理
- **緊急時**: 火災・急病等は予約経路を聞かずに119/110＋施設緊急連絡先を即案内
- **本人確認が必要な案件**（暗証番号・予約変更・返金）は窓口誘導（`directToContact`）
- **予約経路でルールが違う**: 公式予約は当社規約（8日前無料）、OTA予約は各OTA規約。
  AIが経路を1問確認してから案内する（誤約束の防止）
- **コスト保護**: 訪問者ごと 6回/分・50回/日のレート制限＋App Check（reCAPTCHA Enterprise・監視モード）
- **管理者**: Google認証＋email_verified＋@bonfire.co.jp の3層（Rulesテスト22件で担保）

## 4. 主要な不具合と修正（学びのある順）

| 事象 | 原因 | 対処 |
|---|---|---|
| 分岐を押しても無反応 | 選択内容がセッションに記録されるだけで、AIを起動していなかった | 選択意図を最初の訪問者メッセージとして自動送信 |
| 「Property not found」 | 匿名認証の確立前に施設マスタを読み、権限拒否されていた | 認証確立を待ってから取得 |
| Wi-Fiを教えてくれない | 「機密情報」ルールに巻き込まれていた | 鍵コード禁止とWi-Fi案内OKを明確に分離 |
| 駐車場サイズを答えない | 同期ページが7,500字で切られ、末尾の寸法が欠落 | チャンク分割を実装 |
| 404のURLを案内 | プロンプトが「/ja/ を付ける」と*説明*していたためAIが語順を誤った | 5言語×2ページの正しいURLを全列挙し「組み立てるな」と明示 |
| 健全な会話に赤バッジ | 意図確認の段階でエスカレーション判定していた | 誤発火禁止ルールを追加 |
| ↑の修正で今度は必要な窓口誘導まで消えた（**回帰**） | 抑制が効きすぎた | 「発火条件」と「誤発火禁止」を分離して両立 |
| 英語の苦情に日本語で返答 | 強い口調のメッセージで言語判定が揺れた | 「苦情でも言語を変えない」ルールを明記 |
| ログイン名が「匿名」表示 | 移植時に顧客名取得ごと削除していた | 共有Authから表示名を取得しセッションに保存 |
| SIMがタイ語回答を日本語と誤判定（**テスト側のバグ**） | 中黒「・」がUnicode上カタカナ範囲 | 記号除去＋タイ/韓国語を先に判定 |
| 通知メールが届かない会話がある | 機能追加前の会話に `lastMessageAt` が無く、クエリに載らない | `createdAt` フォールバックを追加 |

## 6. 施設の増やし方（takasago で実証済み）

コード変更・デプロイは**不要**。

1. 管理画面「施設」で追加 → 公開ON
2. `admin/properties/{施設}/#chat` で chat用情報（Q&A）を入力
3. 管理画面「写真」で写真を登録（ラベルは「何の写真か＋どんな質問で使うか」を書く）
4. 必要なら公開ページ（how-to/物件）を `chat_site_sources` に登録
5. 管理画面「QRコード」からQRを取得して掲示

**takasago 実績（08/18）**: chatInfo 88行を入力・公開ONするだけで開通。
物件ページ同期の追加のみ実施し、実地テストで施設固有の回答（Wi-Fi・チェックイン・周辺）と
kiyokawa との混線ゼロを確認した。

## 7. 運用（立ち上げ期）

**通知メール**（09/07 実装）: 管理画面「設定」でON/OFF。
- 会話が**10分静穏**になったら、やり取り全文を1通で送信（重複なし）
- **窓口誘導が起きた時点**で即時アラート（【要確認】付き）
- 送信は本体サイトと同じ Gmail SMTP（Secret Manager の SMTP_USER/SMTP_PASS を共用）

**週次の観察**（推奨）:
1. `/admin` の失敗分析 → 知識欠落があれば**正本側**（chat用情報 or How-toページ）に追記
2. Feedback で★3以下のコメントを確認
3. RAGの承認待ちバッジ（L1自動ドラフト）をレビュー

## 8. 未了・保留

- **App Check の強制（enforcement）**: 監視モードで稼働中。検証済み比率を数日見てから判断。
  強制はプロジェクト単位に影響するため、本体アプリ（yah.homes-analytics 未登録）の確認が必要
- **予算アラート**: 未設定
- **写真の自動添付**: 外国語では確実に動作。日本語では文章で説明済みの場合に添付されないことがある
  （実害小・AIの判断としては妥当なため現状維持を選択）
- **Markdown記号の稀な露出**: プロンプトで抑制済みだが確率的に残る。根絶するなら表示側で除去
- **admin/properties の chatInfo**: Wi-Fi行に仕様書のラベル文が混入（動作に支障なし・整形推奨）

## 9. 判断の記録（なぜそうしなかったか）

- **施設ごとに別プロジェクト**: 運用が施設数だけ増える割に利点が無いため不採用
- **admin/templates/#values への相乗り**: values には入室暗証番号など機微情報が混在するため、
  チャットが読むSSoTは「機微情報が構造的に入り得ない場所」に限定する原則で不採用
- **chat管理画面からの property_facts 編集**: 本体側の admin/properties に一本化。
  編集の入口を1つに保つため、chat側には作らない
- **yah.homes/chat/... のパス提供**: Firebase Hosting は1ドメイン1サイトのため、
  本体サイトのデプロイに同梱が必要になり「本体ゼロ影響」の分離が崩れる。サブドメインを採用
